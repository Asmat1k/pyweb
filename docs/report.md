# Отчёт по заданию 1

**Тема задания:** генераторы статических сайтов для публикации результатов исследований.

**Тема исследования:** выбор технологий WebTransport и WebSocket для двунаправленной
передачи данных в веб-приложениях.

**Дата подготовки:** 10 октября 2026 года.

## Цель работы

Освоить Python SSG как инструмент публикации исследовательских материалов,
воспроизводимую сборку и автоматическое развёртывание на GitHub Pages и
отечественном хостинге Helios ИТМО.

## Выбор генератора

Выбран **MkDocs 1.6.1 с Material 9.7.7**: структура Markdown соответствует
исследовательским главам, навигация задаётся в одном YAML-файле, результатом
являются статические файлы. Такой же генератор применён в предложенном образце.
Настройки описаны в [официальной документации](https://www.mkdocs.org/user-guide/configuration/).

SSG переносит генерацию страниц на этап сборки. Хостинг раздаёт готовый HTML,
CSS и JavaScript; Python на сервере публикации не нужен. Для текущей задачи
динамический backend не требуется.

## Содержание сайта

Подготовлены цель и гипотезы исследования, описания транспортов, методика и
сценарии по четырём критериям, сравнительная таблица, ограничения и первичные источники.

Время установки соединения отделено от RTT обмена. Задержка сообщения определена
через эхо-RTT, а ограничения односторонних измерений описаны явно. Для накладных
расходов задан уровень учёта IP и формулы. При потерях анализируются как задержка,
так и доля доставки до дедлайна. Streams и datagrams не смешиваются в одной серии.

Результат этой работы — публикационная инфраструктура и аналитические материалы.
Сетевые эксперименты не выполнялись. Расчёт размера заголовков в
[результатах](results.md) не является экспериментальными данными.

## Исследовательские вопросы по SSG и CI/CD

### Зачем фиксировать версии?

Фиксация ограничивает изменения среды между локальной машиной и CI. Закреплены
также транзитивные зависимости. Для воспроизведения используется та же версия
Python; платформенные различия всё равно могут влиять на установку пакетов.

### Зачем нужен strict?

`--strict` превращает предупреждения MkDocs в ошибку. Конфигурация дополнительно
повышает проблемы ссылок и якорей до предупреждений. Это предотвращает публикацию
с известными ошибками локальной навигации, но не заменяет содержательную проверку
исследования или проверку внешних URL.

### Что даёт автоматизация?

Изменения в `main` запускают одинаковую последовательность установки зависимостей,
сборки и публикации. Сборка pull request выполняется без доступа к SSH-секретам.
При ошибке сборки новая версия не публикуется.

### Чем отличаются два хостинга?

GitHub Pages принимает артефакт через официальный action. Helios принимает те же
статические материалы через SSH/rsync в личный каталог пользователя. Для Helios
нужны SSH-секреты и отдельная сборка с его `SITE_URL`. Генератор на Helios не устанавливается.

### Как ограничен объём работы?

В переданном `task1.md` нет текста P1 и отдельного списка исследовательских вопросов.
Поэтому здесь разобраны вопросы, непосредственно следующие из цели и шагов задания.
Хостинг Helios выбран пользователем. Автоматические тесты и сетевой стенд не добавлялись.

## Статус публикации

Предпросмотр `mkdocs serve` успешно отдал HTTP 200. Команда
`mkdocs build --strict` завершилась с кодом 0. Тема выводит информационный баннер
о MkDocs 2.0; проект использует закреплённую версию 1.6.1, ошибок строгой сборки нет.

Исходники отправлены на GitHub. Статус публикации Pages фиксируется после
фактического запуска workflow.

По указанию пользователя для Helios используется шаблон доступа с заглушками.
Фактическое развёртывание на Helios не выполнялось. Для его завершения требуется
заменить заглушки действительными GitHub Secrets и включить `HELIOS_ENABLED`.
Наличие workflow не считается подтверждением доступности сайта на этом хостинге.
