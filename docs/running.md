# Запуск и публикация

## 1. Python

Для воспроизведения окружения используется **Python 3.15**. На рабочей машине
уже установлен Python 3.15.0, поэтому повторная установка не потребовалась.

```bash
python3 --version
```

Если интерпретатора нет, установите его с [python.org](https://www.python.org/downloads/).
Команды ниже выполняются в терминале из каталога проекта.

## 2. Virtualenv

```bash
python3 -m pip install virtualenv==21.14.6
```

На машине подготовки `virtualenv` уже установлен. Системный Python Homebrew
может запрещать глобальный `pip install`; в такой среде установите virtualenv
через `brew install virtualenv`, не отключая защиту системного окружения.

## 3. Каталог и окружение

При создании проекта с нуля:

```bash
mkdir pyweb
cd pyweb
virtualenv --python python3 .venv
source .venv/bin/activate
```

Для уже клонированного проекта шаг `mkdir` пропускается. В PowerShell активация
выполняется командой `.venv\Scripts\Activate.ps1`.

## 4. Фиксация зависимостей

В `requirements.txt` закреплены версии MkDocs, Material и всех транзитивных
зависимостей. `.gitignore` исключает окружение, `site/`, `_build/` и кэш.

```bash
python -m pip install -r requirements.txt
```

При первоначальной подготовке использовались MkDocs 1.6.1 и Material 9.7.7;
после установки полный список был зафиксирован через `python -m pip freeze`.
Обновление зависимостей выполняется осознанно, с повторной строгой сборкой.

## 5. Каркас сайта

При первом создании был выполнен `mkdocs new .`. Повторять его для готового
репозитория не нужно. Исходники находятся в `docs/`, настройки — в `mkdocs.yml`.
Material обеспечивает русскую навигацию, поиск, светлую и тёмную темы.

## 6. Предпросмотр и строгая сборка

```bash
mkdocs serve
```

Адрес предпросмотра при стандартной конфигурации:
[http://127.0.0.1:8000/pyweb/](http://127.0.0.1:8000/pyweb/).
Остановите процесс через `Ctrl+C`, затем выполните:

```bash
mkdocs build --strict
```

Готовый сайт создаётся в `site/`. В конфигурации предупреждения включены также
для несуществующих локальных страниц и якорей. В CI используется та же команда.
Внешние URL этой командой не проверяются.

## 7. Репозиторий GitHub

Исходный каталог уже содержит Git-репозиторий и remote
`https://github.com/Asmat1k/pyweb.git`, повторная инициализация не требуется.
Обычная последовательность для нового проекта:

```bash
git init -b main
git add .
git commit -m "Add research site"
git remote add origin https://github.com/Asmat1k/pyweb.git
git push -u origin main
```

Для существующего репозитория выполняются только добавление, коммит и push.

## 8. GitHub Actions и GitHub Pages

В **Settings → Pages → Build and deployment → Source** выбрать **GitHub Actions**.
Workflow `GitHub Pages` следует схеме официального шаблона Static HTML, добавляя
установку Python, зависимостей и `mkdocs build --strict` перед загрузкой артефакта.

```text
push main → Python → зависимости → mkdocs build --strict
          → upload-pages-artifact → deploy-pages → GitHub Pages
```

Pull request запускает сборку без публикации. Workflow имеет минимальные права:
чтение исходников, а у задания деплоя — запись Pages и OIDC. Публикуется только
каталог `site/`, без виртуального окружения и исходников проекта.

Целевой адрес: [asmat1k.github.io/pyweb](https://asmat1k.github.io/pyweb/).
Результат публикации проверяется во вкладке
[Actions](https://github.com/Asmat1k/pyweb/actions).

## 9. Отечественный хостинг: Helios ИТМО

Размещение соответствует схеме из репозитория-примера: SSH на
`helios.cs.ifmo.ru:2222`, каталог `~/public_html/pyweb/`, публичный URL
`https://se.ifmo.ru/~ЛОГИН/pyweb/`.

### Настройка доступа

По условиям подготовки проекта реальные учётные данные заменены заглушками.
В этой версии подключение к Helios не выполнялось.

| Параметр | Заглушка для инструкции |
|---|---|
| Логин | `sXXXXXX` |
| Пароль интерактивного SSH | `<HELIOS_PASSWORD>` |
| Приватный ключ CI | `<HELIOS_SSH_PRIVATE_KEY>` |
| Проверенная запись ключа сервера | `<HELIOS_SSH_KNOWN_HOSTS>` |

Пример ручного входа: `ssh sXXXXXX@helios.cs.ifmo.ru -p 2222`.
Пароль вводится интерактивно; в workflow используется отдельный ключ, а не пароль.
Литералы-заглушки не обеспечивают доступ и не должны включаться как действительные секреты.

1. Создать отдельный SSH-ключ для GitHub Actions и добавить его публичную часть
   в `~/.ssh/authorized_keys` своей учётной записи Helios.
2. Получить ключ сервера и сверить отпечаток по доверенному каналу ИТМО.
   `ssh-keyscan -p 2222 helios.cs.ifmo.ru` получает ключ, но сам по себе не проверяет его.
3. В настройках репозитория открыть **Secrets and variables → Actions**.
4. Сохранить секреты `HELIOS_USER`, `HELIOS_SSH_PRIVATE_KEY`, `HELIOS_SSH_KNOWN_HOSTS`.
5. Установить переменную репозитория `HELIOS_ENABLED=true`.
6. Во вкладке Actions запустить workflow **Helios** для ветки `main`.

Приватный ключ не сохраняется в Git. В CI включена строгая проверка ключа сервера.

### Публикация

Workflow повторно собирает сайт с публичным адресом Helios в `SITE_URL`, чтобы
канонические URL и sitemap указывали на правильный хостинг. Относительные ссылки
и ресурсы работают в подкаталоге. Готовые файлы передаются через `rsync`.

Каталог `public_html/pyweb` выделяется только для этого сайта: при синхронизации
устаревшие файлы внутри него удаляются. Остальные учебные работы в `public_html`
не затрагиваются. Если этот подкаталог уже занят, перед первым запуском нужно
выбрать другой путь в workflow и соответствующий `SITE_URL`.

Это простая синхронизация без атомарного переключения релизов: во время копирования
возможен короткий период смешанной версии сайта. Для учебной документации выбран
минимальный вариант без отдельного менеджера релизов.

!!! info "Включение workflow и факт размещения"
    Пока `HELIOS_ENABLED` не установлен, задание публикации пропускается.
    Для завершения размещения нужны действующий доступ к Helios, успешный запуск
    workflow и доступная страница по публичному адресу.
