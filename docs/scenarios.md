# Сценарии экспериментов

Все значения ниже — **предлагаемые параметры эксперимента**. Они не являются замерами.
Точные определения метрик приведены в [методике](methodology.md).

## Матрица условий

| Параметр | Предлагаемые значения |
|---|---|
| Добавленная односторонняя задержка | 0, 10, 25, 50 мс в каждом направлении |
| Независимая потеря IP-пакета | 0; 0,1; 1; 3; 5 % в каждом направлении |
| Полезная нагрузка | 64, 256, 1024 байта |
| Период отправки | 20 мс |
| Повторы | Не менее 5 на комбинацию |
| Таймаут сообщения | 5 с |
| Дедлайн актуальности | 100 мс, отдельно от таймаута |

Добавленные 25 мс в каждом направлении увеличивают RTT примерно на 50 мс,
но итоговый RTT включает исходный маршрут и обработку. В отчёте указываются
и параметры эмуляции, и измеренный базовый RTT.

Перед отправкой datagrams проверяется доступный размер с учётом служебных полей
приложения. Несовместимая комбинация помечается как недоступная; молча уменьшать
полезную нагрузку одного транспорта нельзя.

## Сценарий 1. Установка соединения {#setup}

1. Зафиксировать профиль сети, кэшей и возобновления сессий.
2. Выполнить 100 попыток подключения с таймаутом 10 с на попытку.
3. Сохранить время готовности и первого эха; затем корректно закрыть соединение.
4. Раздельно посчитать успешные подключения, таймауты и другие ошибки.
5. Повторить для каждого транспорта и режима холодного/повторного подключения.

Выход: медиана, p95 и среднее `T_setup`, `RTT_base`, отношение времени подключения
к базовому RTT, доля успешных попыток.

## Сценарий 2. Задержка сообщения {#latency}

После подключения отправляются 200 прогревочных сообщений, затем 10 000 измеряемых
с периодом 20 мс. План отправки не должен ждать эха предыдущего сообщения:
иначе медленная сеть автоматически уменьшит нагрузку и исказит сравнение.
Плановое и фактическое время отправки сохраняются отдельно.

Основное сравнение — один WebSocket и один надёжный двунаправленный поток WebTransport.
Datagrams составляют отдельную серию с другими гарантиями. После последней отправки
приём продолжается 5 с. Выход: медиана, p95/p99 RTT, доля ответов до дедлайна
и число сообщений без ответа.

## Сценарий 3. Накладные расходы {#overhead}

Для каждого размера нагрузки захватывается трафик одной сессии. Первый интервал —
от начала подключения до первого прикладного сообщения; второй — обмен после
прогрева до конца ожидания ответов. Трафик закрытия отмечается отдельно.

Выход: полезные байты по журналам обоих участников, полные IP-байты по захвату,
служебные расходы в байтах и процентах. Сжатие выключено; содержимое сообщений
одинаково. Результаты для сети без потерь и с потерями публикуются раздельно.

## Сценарий 4. Потери пакетов {#loss}

Сценарий задержки повторяется для уровней потерь из матрицы. Дополнительно
выделяется многопоточный случай: один крупный объект передаётся параллельно
с короткими срочными сообщениями при одинаковом общем объёме нагрузки.

В WebSocket оба класса сообщений используют один канал. В WebTransport —
разные надёжные потоки. Этот сценарий исследует независимость потоков;
его результаты не смешиваются с базовым сравнением одного потока.

Выход: изменение p95/p99 относительно сети без потерь, доля сообщений до
дедлайна, таймауты, разрывы и фактическая недоставка datagrams.

## Формат протокола прогона

В метаданных: дата UTC, `run_id`, commit стенда, версии клиента/сервера, транспорт,
режим, размер нагрузки, число сообщений, интервал, RTT, потери, дедлайн и таймаут.
Для каждого сообщения: идентификатор, направление, плановое и фактическое время
отправки, время приёма, полезные байты и статус. Для подключения и захвата — отдельные
сводные записи. Исходные данные пока отсутствуют.
