# WebSocket

## Модель обмена

WebSocket создаёт постоянный двунаправленный канал между клиентом и сервером.
Приложение передаёт текстовые или бинарные сообщения. В базовом варианте соединение
начинается с HTTP/1.1 Upgrade; после ответа `101 Switching Protocols` стороны
обмениваются WebSocket-кадрами. Для защищённого соединения используется `wss://`.
Формат обмена определён в [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html).

```text
Сообщения приложения → WebSocket → TLS → TCP → IP
```

## Подключение

В рассматриваемом холодном соединении последовательно участвуют TCP, TLS и
WebSocket handshake. DNS, проверка сертификата, прокси и кэш браузера также
могут влиять на наблюдаемое время. Момент готовности в браузере — событие `open`.

Число этапов нельзя безоговорочно превратить в фиксированное время:
возобновление TLS и повторное использование соединения меняют картину.
TLS 1.3 описан в [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html).

## Доставка и потери

TCP предоставляет надёжный упорядоченный поток байтов. При потере сегмента
последующие байты ожидают восстановления пропуска: это блокировка начала очереди
(head-of-line blocking). Прикладной эффект — рост задержки сообщений.
Надёжность не означает бесконечное ожидание: соединение может завершиться ошибкой.
Свойства TCP описаны в [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html).

## Накладные расходы

Один WebSocket-кадр имеет базовый заголовок 2 байта, расширенное поле длины
при необходимости и 4 байта маски для направления браузер → сервер.
Кадр с полезной нагрузкой до 125 байт поэтому добавляет 6 байт на клиенте
или 2 байта на сервере. Это только уровень WebSocket: TLS, TCP/IP, ACK и
повторные передачи учитываются отдельно.
См. [RFC 6455, раздел 5](https://www.rfc-editor.org/rfc/rfc6455.html#section-5).

## Прикладные свойства

Для проекта с единым упорядоченным каналом WebSocket даёт понятную модель
сообщений. Логические каналы внутри одного соединения всё равно разделяют его
очередь доставки. Если приложение разделяет их на несколько TCP-соединений,
это уже отдельный сценарий с дополнительными расходами.

Практическая рекомендация: рассматривать WebSocket для чатов, уведомлений и
событий совместной работы, где все сообщения значимы. Подтверждение бизнес-операции
и восстановление после переподключения реализуются на уровне приложения.
