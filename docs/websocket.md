# WebSocket

WebSocket предоставляет постоянный полнодуплексный канал текстовых или бинарных
сообщений между браузером и сервером: обе стороны могут отправлять данные,
не ожидая очередного запроса. Протокол стандартизирован в RFC 6455 в 2011 году.
В этом исследовании рассматривается защищённое соединение `wss://` поверх TLS/TCP.

Материал развивает раздел 2 отчёта НИР (с. 14–19): положение в сетевом стеке,
установление соединения, формат фреймов, жизненный цикл и характеристики.
Теоретические свойства не являются результатами измерений на данном стенде.

## Положение в сетевом стеке

В классическом варианте поверх HTTP/1.1 HTTP используется для начального
рукопожатия. После успешного Upgrade соединение передаётся WebSocket:
последующий обмен состоит из фреймов, без отдельных HTTP-запросов для каждого
сообщения. Надёжность и порядок доставки обеспечивает TCP.

```text
Сообщения → WebSocket → TLS → TCP → IP
```

| Компонент | Роль |
|---|---|
| WebSocket | Границы сообщений, фрагментация, управляющие фреймы |
| HTTP/1.1 | Согласование перехода на WebSocket через Upgrade |
| TLS | Шифрование и проверка сервера в режиме `wss://` |
| TCP | Надёжная упорядоченная доставка байтов, управление потоком и перегрузкой |
| IP | Маршрутизация пакетов |

RFC 8441 и RFC 9220 также определяют установление WebSocket внутри потоков
HTTP/2 и HTTP/3 через расширенный CONNECT. Поэтому свойства TCP ниже относятся
к выбранному для сравнения стеку TLS/TCP; их нельзя автоматически переносить
на WebSocket поверх HTTP/3.

## Установление соединения

Для нового защищённого соединения сначала устанавливается TCP, затем выполняется
TLS-согласование и HTTP-рукопожатие WebSocket.

1. Клиент отправляет GET-запрос с `Upgrade: websocket`, `Connection: Upgrade`,
   `Sec-WebSocket-Version: 13` и `Sec-WebSocket-Key`.
2. Ключ представляет собой случайное 16-байтовое значение в Base64.
   Сервер формирует `Sec-WebSocket-Accept`: добавляет к текстовому значению ключа
   фиксированный GUID из RFC 6455, вычисляет SHA-1 и кодирует результат в Base64.
3. Сервер отвечает `101 Switching Protocols`. Клиент проверяет ответ,
   после чего стороны переходят к обмену фреймами.

```text
Браузер                                      Сервер
   |----------- TCP-рукопожатие ---------------->|
   |<---------- TLS-согласование --------------->|
   |----------- GET + Upgrade: websocket ------->|
   |<---------- 101 + Sec-WebSocket-Accept -------|
   |<========== WebSocket-фреймы ===============>|
```

Ключ и ответ подтверждают корректность согласования протокола, но не
аутентифицируют пользователя и не заменяют TLS. При необходимости стороны
согласуют прикладной подпротокол через `Sec-WebSocket-Protocol`, а расширения,
например сжатие `permessage-deflate`, — через `Sec-WebSocket-Extensions`.

В отчёте приведена ориентировочная оценка 2 RTT для незашифрованного и
3–4 RTT для защищённого холодного подключения. Реальное время зависит от версии
TLS, возобновления соединения, DNS и сетевых условий. В эксперименте готовность
фиксируется по событию `open`, как описано в [методике]({filename}methodology.md).

## Формат фреймов и сообщений

Сообщение WebSocket состоит из одного или нескольких фреймов. Текстовые сообщения
передают UTF-8, бинарные — произвольные байты. Фрагментация сохраняет границы
сообщения и позволяет не собирать весь объём в один фрейм.

| Поле | Размер | Назначение |
|---|---|---|
| `FIN` | 1 бит | Последний фрагмент сообщения |
| `RSV1–RSV3` | 3 бита | Зарезервированы для согласованных расширений |
| `Opcode` | 4 бита | Продолжение `0x0`, текст `0x1`, бинарные данные `0x2`, close `0x8`, ping `0x9`, pong `0xA` |
| `MASK` | 1 бит | Признак маскирования полезной нагрузки |
| `Payload length` | 7 бит и при необходимости ещё 16 или 64 бита | Длина полезной нагрузки |
| `Masking-key` | 0 или 4 байта | Ключ XOR-маскирования при `MASK=1` |
| `Payload data` | Переменный | Данные приложения или управляющего фрейма |

Заголовок без маски занимает 2, 4 или 10 байт; клиентское маскирование добавляет
ещё 4 байта. Общий диапазон — от 2 до 14 байт на фрейм. Клиентские фреймы
маскируются, серверные не маскируются. Маскирование защищает взаимодействие
с промежуточными узлами от ошибочной интерпретации трафика, но не шифрует данные.

Управляющие фреймы ping, pong и close не фрагментируются, их полезная нагрузка
не превышает 125 байт. Они могут передаваться между фрагментами сообщения.
Размеры фреймов не описывают весь сетевой расход: дополнительно учитываются
TLS/TCP/IP, подтверждения, повторные передачи и согласованные расширения.

## Жизненный цикл

| Этап | Поведение протокола | Наблюдение в браузере |
|---|---|---|
| Открытие | Согласование соединения и протокола | `CONNECTING`, затем событие `open` |
| Обмен | Независимая отправка сообщений в обе стороны | `OPEN`, события `message`, вызовы `send()` |
| Проверка активности | Управляющие ping/pong | Браузерный API не предоставляет прямой отправки этих фреймов |
| Закрытие | Обмен close-фреймами, затем закрытие транспорта | `CLOSING`, `CLOSED`, событие `close` |

При штатном закрытии можно передать код и причину завершения. При внезапном
обрыве сети полноценного обмена close-фреймами может не быть. Проверку
актуальности прикладной сессии можно организовать отдельными сообщениями
heartbeat; она отличается от протокольного ping/pong.

WebSocket не выполняет автоматическое переподключение и не восстанавливает
пропущенные сообщения. Приложению нужны правила повторного подключения,
восстановления состояния и подтверждения операций. Успешный `send()` сам по
себе не означает, что сервер применил команду.

## Характеристики и ограничения

| Критерий | Свойство выбранного стека | Значение для приложения |
|---|---|---|
| Доставка | Надёжная, порядок в каждом направлении соединения | Подходит для команд и событий, которые нельзя пропускать |
| Задержка | После открытия нет рукопожатия для каждого сообщения | Затраты подключения распределяются на длительную сессию |
| Накладные расходы | Компактный заголовок фрейма | Относительная доля заголовка растёт для малых сообщений |
| Потери | TCP восстанавливает потерянные байты до выдачи следующих | Одно потерянное звено задерживает последующие сообщения |
| Каналы | Один упорядоченный поток транспорта | Прикладные каналы разделяют одну очередь доставки |
| Смена сети | TCP не предоставляет миграцию соединения | После разрыва требуется восстановление сессии |
| Экосистема | Стабильный стандарт и распространённые реализации | Проще интеграция с существующим сервером и инфраструктурой |

Блокировка начала очереди (head-of-line blocking) означает, что уже полученные
последующие байты не выдаются приложению, пока не восстановлен пропуск.
Разделение сообщений на темы или каналы внутри одного WebSocket не устраняет
эту зависимость TCP. Для обновлений, быстро теряющих актуальность, ожидание
старого сообщения может быть нежелательным.

Пропускная способность зависит от сети, реализации TCP, серверных ресурсов
и обработки сообщений. Малый заголовок не гарантирует преимущество при любой
нагрузке. Рассмотренные в отчёте исследования сравнивают WebSocket с HTTP-опросами
и другими стеками; их результаты не подменяют [измерения проекта]({filename}results.md).

## Безопасность

`ws://` не шифрует обмен; выбранный в исследовании `wss://` использует TLS.
Серверу необходимо проверять `Origin` и права клиента: возможность открыть
соединение со стороннего сайта создаёт риск межсайтового перехвата WebSocket
(Cross-Site WebSocket Hijacking), особенно при аутентификации через cookies.

После рукопожатия фреймы не несут HTTP-заголовков авторизации. Аутентификация
и проверка прав должны быть частью согласованной модели приложения;
при необходимости используются токены и меры против CSRF. Шифрование,
маскирование и проверка пользователя решают разные задачи.

## Когда выбирать WebSocket

В отчёте WebSocket рассматривается как основной кандидат для чатов, уведомлений,
команд, совместных редакторов и панелей мониторинга в стабильной сети, если
достаточно одного надёжного упорядоченного канала. Сильные стороны — зрелая
экосистема, компактное фреймирование и предсказуемая интеграция.

Если нужны независимые потоки, передача без гарантии доставки или устойчивость
при смене сети, следует сопоставить требования с [WebTransport]({filename}webtransport.md)
и проверить поведение в [сценариях экспериментов]({filename}scenarios.md).
