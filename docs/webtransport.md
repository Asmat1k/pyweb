# WebTransport

WebTransport предоставляет браузерный API и модель сессии для двунаправленного
обмена данными. В исследовании рассматривается вариант поверх HTTP/3 и QUIC:
в одной сессии доступны надёжные потоки байтов и ненадёжные дейтаграммы.
Приложение может выбирать гарантии доставки для разных типов данных.

Материал развивает раздел 3 отчёта НИР (с. 20–25): стандартизацию, сетевой стек,
установление сессии, модель передачи, жизненный цикл и характеристики.
Выводы описывают свойства технологии; измерения на стенде ещё не выполнены.

## Стандартизация и поддержка

Транспортный фундамент составляют QUIC (RFC 9000), HTTP/3 (RFC 9114)
и расширение QUIC DATAGRAM (RFC 9221). Браузерный API и отображение сессий
WebTransport на HTTP/3 разрабатываются отдельно в W3C и IETF.

В отчёте зафиксировано состояние на июнь 2026 года: рабочий проект API W3C
и редакция `draft-ietf-webtrans-http3-15`. Поддержка Safari 26.4 завершила
появление технологии в основных семействах браузеров. Это не означает
доступность во всех старых версиях и встроенных браузерах.

!!! info "Уточнение на 12 октября 2026 года"
    API опубликован как [W3C Candidate Recommendation Snapshot от 30 июля 2026 года](https://www.w3.org/TR/2026/CR-webtransport-20260730/).
    Для HTTP/3 опубликован [проект IETF редакции 16](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3-16).
    Эти статусы отличаются от зафиксированных в отчёте и ещё не означают
    окончательную W3C Recommendation или опубликованный RFC WebTransport over HTTP/3.

В отчёте перечислены серверные реализации для Go, Rust, Python и C, а их зрелость
названа менее равномерной, чем у WebSocket. Для проекта следует проверить
совместимость выбранной библиотеки с браузером, поддерживаемую редакцию протокола
и возможности развёртывания HTTP/3. Версии клиента и сервера фиксируются
в [методике]({filename}methodology.md).

## Положение в сетевом стеке

```text
Streams / datagrams → WebTransport → HTTP/3 → QUIC → UDP → IP
                                      TLS 1.3 встроен в QUIC
```

| Компонент | Роль |
|---|---|
| WebTransport | Сессия, API потоков и дейтаграмм |
| HTTP/3 | Согласование сессии через расширенный CONNECT |
| QUIC | Независимые потоки, восстановление потерь, управление перегрузкой, шифрование и миграция |
| UDP | Перенос пакетов QUIC |
| IP | Маршрутизация пакетов |

UDP сам по себе не гарантирует доставку. Надёжность потоков реализует QUIC,
тогда как дейтаграммы используют режим без повторной передачи. TLS 1.3 встроен
в QUIC, поэтому незашифрованного варианта рассматриваемого стека нет.

## Установление сессии

1. Браузер устанавливает QUIC/HTTP/3-соединение либо использует подходящее
   существующее соединение. При новом подключении выполняется рукопожатие QUIC
   с криптографическим согласованием.
2. Стороны согласуют поддержку необходимых расширений HTTP/3.
3. Клиент отправляет расширенный CONNECT к ресурсу WebTransport.
   Сервер проверяет запрос и источник, затем принимает или отклоняет сессию.
4. После успешного ответа приложение получает готовую сессию и может работать
   с потоками и дейтаграммами.

```text
Браузер                                      Сервер
   |<---------- QUIC + TLS 1.3 ----------------->|
   |<---------- HTTP/3 SETTINGS ---------------->|
   |----------- расширенный CONNECT ------------>|
   |<---------- успешный ответ 2xx ---------------|
   |<========== потоки / дейтаграммы ===========>|
```

Готовность в браузере определяется выполнением `transport.ready`.
Сокращение транспортного рукопожатия — возможное преимущество QUIC,
но время до готовности включает также установление сессии HTTP/3.

!!! note "Рукопожатие QUIC и готовность WebTransport"
    Оценки 1 RTT и 0 RTT в отчёте относятся к возможностям QUIC. Их нельзя
    считать гарантированным временем до `transport.ready`. Редакция 16
    [WebTransport over HTTP/3, раздел 3.2](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3-16#section-3.2)
    запрещает инициировать сессию CONNECT в пакетах 0-RTT.

После установления сессии открытие потока не требует отдельного рукопожатия,
но может ожидать доступного лимита потоков или разрешения управления потоком.
Холодное подключение, повторное подключение и использование существующего
соединения нужно измерять отдельно.

## Потоки и дейтаграммы

| Свойство | Streams | Datagrams |
|---|---|---|
| Доставка | Надёжная, порядок внутри потока | Без гарантии доставки и порядка |
| Направление | Однонаправленные и двунаправленные потоки | Отправка и приём в рамках сессии |
| Границы сообщений | Задаёт приложение | Сохраняются |
| Потери | Восстановление данных затронутого потока | Пропуск без транспортной повторной передачи |
| Применение | Команды, документы, независимые надёжные передачи | Обновления с ограниченным сроком актуальности |

### Надёжные потоки

Каждый поток переносит упорядоченную последовательность байтов. Общего порядка
между разными потоками нет. Однонаправленный поток передаёт данные только
от создавшей его стороны, двунаправленный допускает обмен в обе стороны.

QUIC переносит данные фреймами STREAM: идентификатор потока и смещение позволяют
собрать байты в правильном порядке и восстановить пропуски. В начале потока
служебный префикс связывает его с сессией WebTransport. Далее передаются
прикладные байты, поэтому границы записей следует задавать самостоятельно,
например длиной сообщения перед его содержимым. Границы чтения из потока
не обязаны совпадать с границами записей приложения.

Потеря данных задерживает доставку внутри затронутого потока, но не требует
ждать эти байты для выдачи данных другого потока. Если все сообщения поместить
в один поток, упорядочивание и ожидание восстановления внутри него сохранятся.

### Ненадёжные дейтаграммы

Дейтаграмма — отдельная запись с сохранением границ. QUIC не повторяет её
передачу при потере и не восстанавливает порядок. Это подходит для телеметрии
и обновлений состояния, когда новое значение заменяет старое.

Приложению нужны правила обработки пропусков, запоздавших данных и перестановок:
например, номер последовательности и срок актуальности обновления. Дейтаграммы
не гарантируют прибытие к дедлайну. Перед отправкой проверяется допустимый размер,
доступный через `transport.datagrams.maxDatagramSize`; крупные записи требуют
потока либо отдельной прикладной схемы разбиения.

## Фреймирование и привязка к сессии

В отличие от WebSocket, WebTransport не задаёт единый заголовок для каждого
прикладного сообщения. Он использует механизмы QUIC и HTTP/3. Сессия связана
с CONNECT-потоком, а служебные идентификаторы направляют данные нужной сессии.
Таблица развивает таблицу 6 отчёта (с. 23–24); названия сигналов зависят
от редакции спецификации.

| Фрейм или сигнал | Уровень | Назначение |
|---|---|---|
| STREAM (`0x08–0x0f`) | QUIC | Данные потока, идентификатор, смещение и признак завершения |
| DATAGRAM (`0x30–0x31`) | QUIC | Дейтаграмма без упорядочивания и повторной передачи |
| Префикс двунаправленного потока (`0x41`) | Отображение на HTTP/3 | Связывает поток с Session ID; в отчёте назван `WEBTRANSPORT_STREAM` |
| Тип однонаправленного потока (`0x54`) | Отображение на HTTP/3 | Обозначает поток WebTransport; далее следует Session ID |
| HEADERS (`0x01`), SETTINGS (`0x04`) | HTTP/3 | Заголовки CONNECT и согласование возможностей соединения |

Число байтов служебных полей зависит от формата пакета, переменной длины
идентификаторов и объединения фреймов. Накладные расходы нельзя оценивать одним
фиксированным «заголовком WebTransport»: учитываются QUIC, UDP/IP, криптографическая
защита, подтверждения и повторная передача данных потоков.

## Жизненный цикл

| Этап | Поведение |
|---|---|
| Создание | Объект WebTransport начинает установление сессии |
| Готовность | Выполнение `transport.ready` разрешает обмен |
| Передача | Создание и приём потоков, отправка и приём дейтаграмм |
| Завершение потока | Завершает отдельную передачу, сохраняя возможность других обменов |
| Завершение сессии | `transport.close()` инициирует закрытие; `transport.closed` отражает завершение или ошибку |

Сессия и транспортное соединение — разные сущности: завершение одной сессии
не обязательно закрывает общее HTTP/3-соединение. Контроль активности
и обнаружение транспортного обрыва обеспечиваются QUIC; подтверждение применения
команды всё равно требует прикладного ответа.

QUIC предусматривает миграцию соединения при изменении сетевого пути,
например при переходе с Wi-Fi на мобильную сеть. Это возможность сохранить
соединение, а не гарантия пережить любой разрыв: результат зависит от реализации,
проверки нового пути, тайм-аутов и доступности сервера.

## Характеристики и ограничения

| Критерий | Свойство | Практическое следствие |
|---|---|---|
| Подключение | QUIC объединяет транспортное и криптографическое рукопожатия | Возможное сокращение холодного старта; измеряется полная готовность сессии |
| Потери | Восстановление внутри потока; дейтаграммы не переотправляются | Можно разделять независимые передачи и отбрасывать устаревшие обновления |
| Режимы доставки | Потоки и дейтаграммы в одной сессии | Гарантии выбираются по типу данных |
| Миграция | Поддержка смены пути на уровне QUIC | Потенциально меньше переподключений у мобильных клиентов |
| Ресурсы | Обработка QUIC и криптографии, служебный трафик | Результат зависит от реализации и профиля нагрузки |
| Инфраструктура | Рассматриваемый стек требует доступности UDP/HTTP/3 | Фильтрация UDP ограничивает применимость |

Все потоки и дейтаграммы используют общий контроль перегрузки соединения.
Устранение зависимости от потерянных байтов другого потока не устраняет
конкуренцию за полосу, общие лимиты и задержки обработки.

В отчёте приведено исследование Zhang и соавторов о снижении пропускной
способности QUIC на высокоскоростных каналах. Оно сравнивает конкретные реализации
TCP + TLS + HTTP/2 и UDP + QUIC + HTTP/3; переносить процент снижения на любое
приложение WebTransport нельзя. Нагрузка на CPU и сетевой расход проверяются
по общей [методике]({filename}methodology.md).

## Безопасность

QUIC использует обязательную криптографическую защиту TLS 1.3. Проверка источника
браузерного запроса входит в установление сессии: сервер проверяет `Origin`
до её принятия. Это не заменяет аутентификацию пользователя и проверку прав
на прикладные операции.

В отчёте отдельно обсуждается риск повторного воспроизведения ранних данных
QUIC 0-RTT. Поддержка такой возможности транспортом не означает разрешение
открыть WebTransport-сессию в 0-RTT: ограничение CONNECT описано выше.

## Когда выбирать WebTransport

В отчёте технология рассматривается как кандидат для потоковой телеметрии,
нескольких независимых каналов и мобильных клиентов с нестабильной сетью.
Команды, требующие подтверждения, можно передавать потоком, а быстро устаревающие
обновления — дейтаграммами в той же сессии.

Перед выбором проверяются доступность UDP, совместимость браузеров и сервера,
необходимость разных режимов доставки и фактические затраты на нагрузке проекта.
Если достаточно одного надёжного канала, стоит сопоставить эти затраты
с [WebSocket]({filename}websocket.md). План проверки приведён в
[сценариях экспериментов]({filename}scenarios.md), статус измерений — на странице
[результатов]({filename}results.md).
