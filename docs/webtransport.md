# WebTransport

## Модель обмена

WebTransport предоставляет браузеру однонаправленные и двунаправленные потоки,
а также дейтаграммы. Здесь исследуется отображение поверх HTTP/3 и QUIC.
API описан в [спецификации W3C](https://www.w3.org/TR/webtransport/),
протокол — в [WebTransport over HTTP/3](https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/).

```text
Сообщения приложения
        ↓
WebTransport: streams / datagrams
        ↓
       HTTP/3
        ↓
 QUIC (с интеграцией TLS 1.3)
        ↓
        UDP
        ↓
         IP
```

## Два режима с разными гарантиями

| Свойство | Streams | Datagrams |
|---|---|---|
| Представление | Поток байтов | Отдельная дейтаграмма |
| Надёжность | Восстановление потерянных данных | Без повторной передачи потерянной дейтаграммы транспортом |
| Порядок | Внутри каждого потока | Не гарантируется |
| Границы сообщений | Задаёт приложение | Сохраняются |
| Подходящая нагрузка | Команды, документы, независимые надёжные каналы | Обновления состояния с ограниченным сроком актуальности |

Отсутствие повторной передачи не отменяет контроль перегрузки QUIC.
Дейтаграммы могут быть отброшены; их размер ограничен согласованными параметрами
и возможностями пути. См. [RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html).

## Подключение

Готовность браузерной сессии определяется выполнением `transport.ready`.
Она включает не только QUIC handshake, но и согласование WebTransport.
Поэтому поддержка ранних данных в QUIC не означает гарантированную готовность
WebTransport за 0 RTT. Холодное подключение и возобновление следует измерять раздельно.

## Поведение при потерях

Внутри надёжного QUIC-потока потерянные байты задерживают последующие данные.
Другой поток может продолжать доставку независимо от порядка первого. Общий
контроль перегрузки и ограничения соединения при этом сохраняются.
QUIC не устраняет все источники задержки при потерях.
См. [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html).

## Прикладные расходы

Поток байтов требует собственного формата сообщений: например, префикса длины,
идентификатора и полезной нагрузки. Дейтаграммы требуют обработки пропусков
и переупорядочивания. Эти расходы входят в сравнение наряду с сетевыми заголовками.

Для развёртывания HTTP/3-варианта необходимы сервер с поддержкой соответствующей
версии WebTransport, сертификат и доступность UDP. Наличие HTTP/3 у обычного
веб-сервера само по себе не подтверждает поддержку WebTransport.

!!! note "Фиксируйте версию реализации"
    W3C API и спецификация WebTransport over HTTP/3 развиваются. В протоколе
    эксперимента нужны версии браузера, сервера и поддерживаемой редакции протокола.
